## Pre-commit hooks (Husky)
- **pre-commit** (`.husky/pre-commit`): runs `npm run lint` then `npm test` on **separate lines** (not `&&`-chained) — a lint failure does NOT block the commit if tests pass, because the hook's exit code is that of the last command. Use `git commit --no-verify` to bypass.
- **commit-msg** (`.husky/commit-msg`): if a commit touches both test files (`*.test.*`) AND source files (`*.ts`, `*.tsx`), the message must start with `[RED]` or `[GREEN]`. Otherwise the hook rejects. Always split mixed commits or use `--no-verify`.

## Architecture
- **Entry**: `index.html` → `index.tsx` → `App.tsx`. The root returns `<SetupScreen />` (V2, wrapped in `ToastProviderV2`) when `VITE_SETUP_MODE=true`, else `<LandingScreen>` (V2 splash, once per session) then provider stack → `<AppShellV2 />` (V2 stage router). **The live UI is the `components/v2/` tree ("Emberlight V2", branch `ui-update`)**; all pre-V2 screens/layouts remain as un-imported dead code (tests still pass). Revert = revert `App.tsx` + `index.html` (the only two pre-existing files modified).
- **Provider order (must be preserved)**: `AuthProvider > UIProvider > GameProvider > ProgressionProvider > CampaignProvider > ActionsProvider`. Each consumes contexts above it.
- **State**: No external lib (no Redux/Zustand). 6 React Contexts, each backed by a custom hook. `GameContext` composes `useGameState` only (the legacy `useQueue` hook was removed when the queue system was replaced by chat-native pending messages). `getSenderName` (formerly in `useQueue`) now lives in `useGameState` — it labels solo USER messages.
- **Engine**: `MockMCPServer` (`services/mcpService.ts`) is the single canonical source of truth for `GameState`. Never mutate `gameState` directly — always go through `mcpServer.executeToolCall` or its typed wrappers.
- **Effect Dispatcher** (`services/effectDispatcher.ts`): hook-aggregator evaluation engine. Reads effect payloads (`effect: { kind, payload }`) from race/class/subclass/feat catalogs at runtime and folds them into typed hook contexts at well-defined event points (`onAttackRoll`, `onAttackDamage`, `onDamageTaken`, `onSaveRoll`, `onSkillCheck`, `onConditionApplied`, `computeAc`, `computeSpeed`, `computeMaxHp`, `onCharacterCreated`, `onLongRest`, `onShortRest`, `onLevelUp`). Two public APIs: `applyEffects(char, hook, ctx)` — folds matching effect payloads through registered per-kind reducers into a typed context; `getEffects(char, kind)` — collects raw payloads from all 4 sources (race traits, class features, subclass features, **and subrace traits**) for inline logic. Eliminates hardcoded class-ID/race-ID/feat-ID branches from engine services. Notable reducers: `damage-resistance` supports condition-gating (`condition: 'raging'`) and placeholder resolution (`from-draconic-ancestry` → `character.draconicDamageType`); `crit-bonus-dice` accumulates a counter (`_extraCritDiceCount`) that the caller rolls as weapon dice; `crit-range` sets `_critRangeExpanded` only when `roll >= minCrit` — combat reads the flag directly (NOT a hardcoded `>= 19`), so Champion Superior Critical (18-20) crits on 18; `reroll-ones` is registered on `onAttackRoll`, `onSkillCheck`, AND `onSaveRoll` (Halfling Lucky rerolls natural-1 saves too — `make_save` rolls the d20 before `applyEffects` so the reducer sees it) and uses `cryptoRoll` (not `Math.random`) so the reroll is bias-free and mockable via the standard `cryptoRoll` pattern; `speed-bonus` checks armor conditions via `meetsCondition()`; `skill-expertise` adds proficiency bonus for skills with rank > 1; `jack-of-all-trades` adds half proficiency bonus to non-proficient skills; `reliable-talent` floors proficient skill d20 rolls at 10; `fighting-style` applies Defense (+1 AC in armor), Archery (+2 attack — written to `ctx.attackBonus`, NOT the natural die, so `isCrit` checks the true d20 and a natural 18 archer can't fake a crit), Dueling (+2 melee dmg); `diamond-soul` adds save proficiency across all stats; `metamagic-option` is registered on BOTH `onCharacterCreated` AND `onLevelUp` so metamagic survives level-up; **`aura-of-protection`** is applied cross-character in `combatService.make_save` (scans party for conscious Paladins L6+, adds highest CHA mod to saves); **`evasion`** is applied in `spellcastingService` save-damage path (0 dmg on successful DEX save, half on failure). New classes/races/subclasses/feats can add standard effects with catalog data alone — no engine code changes.
- **Resource Handlers** (`services/resourceHandlers.ts`): registry of `use_resource` handlers (second-wind, rage, lay-on-hands, breath-weapon, ki/stunning-strike/flurry-of-blows/patient-defense/step-of-the-wind, bardic-inspiration, channel-divinity, hellish-rebuke, wild-shape, sorcery-points, action-surge, indomitable, divine-sense, arcane-recovery, natural-recovery, relentless-endurance). Called via `RESOURCE_HANDLERS[resourceId](ctx, characterId, targetId, amount)` from `spellcastingService.use_resource`. Adding a new spendable resource = one handler function, zero changes to the spellcasting module. The `INFO_ONLY_RESOURCES` set (`arcane-recovery`, `natural-recovery`) marks handlers that return capacity info only — `spellcastingService.use_resource` skips the `classEngineSpendResource` eager-spend for these so the pool charge isn't consumed before the modal path runs.
- **Sub-services**: `services/mcp/` — DI-style factories (`createXService(state, deps?)`) closing over shared state. 8 sub-services wired in `mcpService.ts:45-75`. All share the same mutable `state: GameState` reference. Cross-service deps use 4 interfaces: `InventoryDeps`, `CombatDeps`, `SpellcastingDeps`, `TravelDeps`. The `getTarget` function is always `this.party.getTarget`.
- **Deep clone**: `JSON.parse(JSON.stringify(...))` is the universal pattern for state snapshots, rewinds, and transactions (~20 uses). No `structuredClone`, no immutable lib.
- **Path alias**: `@/*` → repo root (not `src/`). Both `tsconfig.json` and `vite.config.ts` agree.

## State management patterns
- **`syncState()`** (GameContext): reads `mcpServer.getFullState()` → `setGameState()`. Pulls engine state into React. No persistence.
- **`syncFinished()`** (useGameActions private): attaches ctx metadata, sets `isProcessing: false`, deep-clones, calls `mcpServer.loadState()` + `setGameState()` + `storageService.syncCampaignState()`. Persists. The `extras` param accepts `lastSuggestionsByCharacter` (per-player suggestion map, new source of truth) in addition to the deprecated `lastSuggestions`. The `actionQueue` extra was removed with the queue system.
- **`syncCampaignState()`** (storageService): writes to Supabase or localStorage depending on `campaignId !== 'anonymous'`.
- **Two independent `processingRef`s**: `useGameActions` guards against concurrent `handleSendMessage` calls. `useGameState` `isProcessingRef` guards Supabase realtime subscription — incoming remote state is skipped when local processing is active.
- **Remote processing pre-check**: before setting `processingRef.current = true`, both `handleSendMessage` (solo path) and `handleProcessBatch` call `storageService.isCampaignProcessing(campaignId)` (a SELECT on Supabase) to verify no other player has started processing since the last realtime sync. Gated by `isSyncableCampaign` — anonymous campaigns skip the check entirely. Fail-open: returns `false` on error so a Supabase outage doesn't block gameplay. Narrows the distributed lock race window from "since last realtime update" to one round-trip.
- **Realtime messages guard**: `setMessages(remoteMessages)` runs inside the `isProcessingRef` apply branch so heartbeat echoes during an in-flight turn can't clobber local placeholder/tool messages.
- **Lock self-heal**: `isProcessingLockedAt` timestamp is stamped when the realtime lock is engaged. A 180s `setInterval` watchdog force-clears `isProcessingRef` if stuck, preventing permanent realtime lockout from a dropped unlock payload.
- **Fresh-load safety**: `loadGameData` strips persisted `isProcessing`/`processingUser` on hydration so a frozen `isProcessing: true` never boots the UI into a processing state on refresh.
- **`loadGameData` returns `Promise<boolean>`** (`hooks/useGameState.ts:43`): returns `true` when campaign data was found and loaded, `false` otherwise. Callers (e.g. the join flow) use this to decide whether to proceed — the join path alerts "Campaign not found" when false.
- **`handleJoinCampaign` `joinAsNewMember` flag** (`hooks/useCampaigns.ts:75`): when `true` and the campaign loads successfully and the user does NOT already own a character (re-join guard), the hook sets `isNewCampaign=false` + `stage=START_MODE`. This routes the joiner through the same Quick Start / Customize choice the host sees. Quick Start in join-mode (`QuickStartFlow isNewCampaign={false}`) skips the starting-grounds step (the host already picked one) and finalizes the preset immediately using `campaignStartingLocation={gameState.startingLocation}`. The "Switch to Custom" button still routes to `WizardShell` (`stage=CREATION`). If the user already owns a character in the loaded party, the wizard is skipped entirely (loadGameData already set stage to PLAY). `handleSelectCampaign` (Resume) always passes `false`.
- **`messagesRef` stale closure pattern**: `handleSendMessage` reads from `messagesRef.current` (a ref mirror of `messages`) instead of the closure-captured variable. It is NOT wrapped in `useCallback`. `handleSendMessageRef` pattern passes latest version to `handleRewind`. `restoreToBeforeLastTurn` synchronously updates `messagesRef.current` after rewinding the messages array so the auto-retry captures the rewound list deterministically.
- **`ctxRef` / `ctxLoadedRef` / generation rewind protocol**: Context manager state lives in a ref, hydrated once from `gameState.ctx` on mount. `generation` is bumped on rewind — syncs are tagged with generation, remote clients discard stale updates where `_rewindGeneration < local generation`.
- **`handleSendMessage` is NOT wrapped in `useCallback`** — it's a plain async function inside `useGameActions`, recreated every render.
- **`handleProcessBatch` parity with `handleSendMessage`**: both code paths share the same patterns — `enableSuggestions`, `withNarrationRetryTimeout` on narration retries, `syncState()` in `finally`, `mcpServer.getFullState()` in error handler. The batch path additionally fetches the latest Supabase messages (`storageService.fetchMessages`) before promoting pending messages to catch any pending items added by other players during the click race window. The fetch happens BEFORE `processingRef.current = false` to prevent a realtime message-clobber window.
- **`handleRewind` batch routing**: returns a discriminator `{ kind: 'solo', text } | { kind: 'batch' } | null`. A solo rewind re-sends `text` through `handleSendMessageRef`; a batch rewind re-runs `handleProcessBatchRef`. Batch detection: snapshot's trailing message has `pending: true` (snapshots are saved BEFORE promotion); emergency path falls back to walking back from the last MODEL message tagged `batchTurn: true`.
- **Rewind batch restore**: `restoreToBeforeLastTurn` restores `snapshot.messages` verbatim for batch turns (no slice — pending messages stay pending and re-editable). For solo turns it strips the trailing user message (`slice(0, -1)`) so the retry can re-add it. Rewind generation is bumped before restore; both Supabase and anonymous paths persist the restored message list.
- **`isSyncableCampaign`**: `campaignId != null && campaignId !== 'anonymous'`. The literal `'anonymous'` gates the entire cloud/local persistence split.

## Known Multiplayer Limitations
- **`fetchMessages` pending race window**: pending messages added by other players in the ~50ms window between `fetchMessages` and `syncFinished` in `handleProcessBatch` may be lost. Requires a server-side atomic merge (stored procedure) to truly close.
- **`ctxRef` cross-client sync (now mitigated)**: when another player processes a turn, their advanced `ctx.turnCounter` + checkpoints are written to the shared blob. The hydration `useEffect` in `useGameActions` now re-hydrates `ctxRef` from remote state when `remoteTurnCounter > local` (issue 12 fix). Residual: only the persistent fields are adopted; transient `isCompressing`/`compressPromise` stay local. Concurrent-turn last-writer-wins can still diverge briefly (same consistency model as game state itself).
- **Optimistic turn lock (not atomic)**: the `isCampaignProcessing` pre-check narrows the race to one round-trip but two players can still both pass it. A true fix needs a Supabase RPC (`UPDATE ... WHERE isProcessing = false`); deliberately NOT added to avoid backend/migration risk. The 180s self-heal watchdog remains.
- **Collaborative batch turns are single-round**: `next_turn` breaks the agent loop immediately. Actions spanning multiple combat rounds should be queued in separate batches. The LLM batches all single-round tool calls in parallel before `next_turn`, so same-round actions work correctly.
- **GM notes need host plumbing**: `Character.gmNotes` + `NotesPanel` exist and are host-gated via an `isHost` prop. Host plumbing IS now wired: `loadGame` reads `host_id` from the campaigns row → `SavedGameData.hostId` → `useGameState.hostId` (exposed via `GameContext`) → layouts pass `isHost={!!userId && userId === hostId}` to `CharacterSheet` → `NotesPanel`. Personal `notes` are owner-gated by `ownerId === userId` and work in all modes (including anonymous, where `isHost` is false so only personal notes show).
- **Chat state sync (now mitigated)**: previously, "The Fates are deciding..." loading indicator and dice roll modal popups only appeared on the client that triggered processing. Fixed by: (1) `ChatLog` now receives `isProcessing={isLoading || !!gameState.isProcessing}` so remote clients show the loading indicator when `gameState.isProcessing=true` arrives via Supabase realtime; (2) `ChatLog` auto-triggers the `<DiceRollModal>` popup for any new message carrying `rollData` — this runs on every client (local + remote via realtime), so all players see the animation, not just the submitting client. `DiceRollCard` remains clickable for replay. The `rollData` itself is persisted in messages and rendered inline for all clients.

## Multiplayer Attribution & Hardening
The engine is **state-correct but attribution-soft** — it trusts the LLM to pass the correct actor id per tool call, silently defaulting to `party[0]` when omitted. The following hardening was added (all conditional on `party.length > 1`, so solo is byte-identical unless noted):
- **`MULTIPLAYER_PROMPT`** (`services/llm/prompts/multiplayerPrompt.ts`): injected into the system message ONLY when `state.party.length > 1` (`agentLoop.ts`). Makes the attribution contract explicit (map `[CharName]` prefixes → ids; always pass `attackerId`/`casterId`/`targetId`). Also instructs the LLM to use `suggestionsByCharacter` on `narrate_turn` (a `Record<charId, string[]>`) instead of the flat `suggestions` array, so each player gets class-appropriate chips.
- **Per-player suggestions** (`services/llm/suggestions.ts`): `resolveSuggestionsPerCharacter` produces a `Record<characterId, string[]>` stored on `GameState.lastSuggestionsByCharacter`. Each client reads its own slice via `pickSuggestionsForCharacter(state, myCharacterId)`. The deterministic generators are class-aware: Rogue chips differ from Cleric chips. Solo collapses to a single-entry record (one unified code path).
- **`PARTY:` context line** (`agentLoop.ts`): a clean per-character summary `name (hp/max HP, AC N) [conditions]` mirroring the `ENEMIES:` line, computed via `calculateAc`. Additive — also helps solo (the LLM previously had to guess each member's AC).
- **Enriched batch context** (`buildBatchContextString` in `gameActionHelpers.ts`): emits `ACTIVE CLASS FEATURES / RESOURCES / SPELLS / FEATS / PERSONA` for EVERY party member (the old batch path only sent raw party JSON + world). `buildCharacterEnrichment(char)` was extracted from the solo `buildContextString` (refactor is output-identical for solo).
- **Actor-id warn-stamp** (`mcpService.executeToolCall`): when `party.length > 1` and an actor tool (`player_attack`, `cast_spell`, `check_skill`, `make_save`, `update_inventory`, `adjust_currency`, `short_rest`, `manage_spellbook`, `level_up`, `use_resource`, `roll_death_save`) is called with NO actor id, a `WARNING: ... applied to <party[0].name>` is appended to `result.message`. The LLM sees it via `formatToolResult` and self-corrects. Never alters success/failure. `long_rest` is EXCLUDED (party-wide by design). XP is engine-driven (no LLM tool).
- **`QueuedAction.userId`** (`types/common.ts` — REMOVED): the queue system was removed in favor of chat-native pending messages (`Message.pending: true`). The `QueuedAction` type no longer exists; legacy `actionQueue` items in old saves are converted to pending USER messages on load via the `loadGameData` migration.
- **`getTarget` ambiguity warning** (`partyService.ts`): when a name matches 2+ members, logs a warn. Resolution order is UNCHANGED (first match) so no existing campaign behavior shifts.
- **Sheet `isProcessing` banner** (`CharacterSheet.tsx`): soft, non-blocking warning when `gameState.isProcessing` — edits remain enabled (the inventory/currency race is made visible, not blocked).
- **Per-player pending-message send** (`handleSendMessage` multiplayer branch): when `party.length > 1` and the send is NOT a rewind retry, the USER message is appended with `pending: true` instead of triggering the LLM. The local player's suggestion chips are cleared immediately (only their entry in `lastSuggestionsByCharacter` is deleted — others' chips remain). Any player can later press "Take the Turn" (`handleProcessBatch`) to flush all pending messages through one LLM turn. Pending messages are owner-removable via `handleRemovePendingMessage` until processing starts. The `isRetry` guard ensures rewind re-sends go straight to the LLM.
- **Per-player notes** (`Character.notes` / `gmNotes` + `NotesPanel`): private-by-convention — UI renders `notes` only for `ownerId === userId`, `gmNotes` only for `isHost` (`userId === hostId`, plumbed from the campaigns row's `host_id` via `loadGame` → `useGameState.hostId` → `GameContext`). Both are STRIPPED from LLM context via `withoutPrivateNotes()` in `gameActionHelpers.ts` (buildContextString + buildBatchContextString). True cryptographic privacy needs a separate RLS-gated table.

## Multiplayer Pending-Batch Chat (replaces the queue system)
The dedicated multiplayer queue (`useQueue`, `ActionQueuePanel`, Queue Action/Queue Dialogue buttons, queue drawer/section in layouts) was REMOVED. The replacement is a **chat-native pending-batch system** that uses the existing chat log as the holding tank. Active only when `party.length > 1` (solo is byte-identical to before).
- **`Message.pending?: boolean`** (`types/common.ts`): marks held USER messages that have NOT yet been sent to the LLM. Filtered out of LLM context (`prepContext` receives `messages.filter(m => !m.pending)`). Rendered in `ChatLog` with a dashed amber border + "Pending" pill + owner-gated × delete button.
- **`Message.batchTurn?: boolean`** (`types/common.ts`): tags the MODEL narration that concludes a collaborative batch turn, so `handleRewind` routes retries back to `handleProcessBatch` instead of the solo `handleSendMessage` retry path.
- **`handleSendMessage` multiplayer branch**: when `party.length > 1 && !isRetry`, the USER message is appended with `pending: true` (no LLM call). Local chips clear via per-player `lastSuggestionsByCharacter` deletion. Rewind re-sends bypass this branch via `isRetry=true` and go straight to the LLM.
- **`handleProcessBatch`** (`useGameActions.ts`): the new batch processor. Any player can press "Take the Turn" to flush all pending messages. Flow: optimistic-lock pre-check → `fetchMessages` (race-window preservation for pending msgs added by other players in the click race window) → `isProcessing: true` lock → build aggregated batch text `[Collaborative Turn]\n[Name]: text` → promote pending msgs (`pending: false`) → `runAgentLoop` → narration tier chain → per-character suggestions → `syncFinished` with MODEL msg tagged `batchTurn: true`.
- **`handleRemovePendingMessage`** (`useGameActions.ts`): owner-gated removal of a pending message. No-op for non-owners, non-pending, or once processing has started.
- **`loadGameData` migration** (`useGameState.ts`): on hydration, any legacy `actionQueue` items in old saves are converted to pending USER messages (`pending: true`, `senderName = playerName`), and `actionQueue` is stripped from the loaded state. One-time; the field is never re-persisted.
- **`fetchMessages`** (`storageService.ts`): SELECT on the `messages` JSONB column. Used by `handleProcessBatch` to capture pending messages added by other players during the click race window (mirrors the legacy `fetchGameState` queue-preservation pattern). Returns `null` on error.

## Multiplayer Presence (typing indicators)
Brand-new capability built on Supabase Presence (ephemeral, broadcast-only — no DB writes, no migrations). Active only for syncable multiplayer campaigns.
- **`hooks/usePresence.ts`**: subscribes to a per-campaign presence channel (`presence-${campaignId}-typing`). Each client tracks `{ userId, characterId, name, portraitUrl, isTyping, lastActive }`. Typing is announced on the **first keystroke** and stays active for **10s after the last keystroke** (no flickering on every keypress — subsequent strokes within the window just reset the idle timer without re-broadcasting). Stale entries pruned after 30s. Excludes the local user (you never see your own indicator) and dedups by `userId` (a player with multiple tabs counts once). **Stable channel lifetime**: the channel `useEffect` depends on the primitive `myCharacter?.id` (NOT the deep-cloned `Character` object, whose identity flips every `gameState` sync and would tear down/rebuild the channel constantly, dropping in-flight `track({isTyping:false})` calls). Fresh character data is read inside `buildProfile` via a `myCharacterRef` updated in a separate small effect. **Hardened against WebSocket drops**: auto-reconnect with exponential backoff (1s→2s→4s→8s, max 30s) on `CHANNEL_ERROR`/`TIMED_OUT`/`CLOSED` subscribe statuses; re-subscribe on `navigator.online`; re-broadcast current profile on tab visibility change; periodic heartbeat every 10s (only when typing) to prevent stale presence entries; `track()` is awaited with one retry on failure; debug logging gated by `isDebugMode`. Listens to `sync`, `join`, and `leave` presence events for immediate indicator updates.
- **`components/shared/TypingIndicator.tsx`**: row of compact "NAME is writing…" chips, each leading with the typing character's portrait (or first initial when no portrait) + three bouncing dots. Hidden entirely when empty. Rendered above `InputArea` in both layouts.
- **Wiring**: layouts compute `myCharacterForPresence` (gated on `isMultiplayer`), call `usePresence(currentCampaignId, userId, isMultiplayer, myCharacterForPresence)`, and pass `setTyping` to `<InputArea onInputChanged={(v) => setTyping(v.length > 0)} />`. The InputArea fires `onInputChanged` on every keystroke AND on send/clear: `handleSubmit` calls `onInputChanged?.('')` after `setInput('')` (without this, `setInput('')` doesn't fire `onChange`, so the remote indicator would linger until the 30s stale threshold). Quick-action pre-fills and speech-to-text results likewise call `onInputChanged` so the indicator reflects the true input state.

## LLM Agent Loop (`services/llm/agentLoop.ts`)
- **`MAX_ITERS = 20`**, 60s timeout per iteration, `temperature: 0.7`, `tool_choice: "auto"`.
- **Prompt assembly order**: system (SYSTEM_INSTRUCTION + PROGRESSION_SYSTEM_PROMPT + TOOL_MODE_INSTRUCTION +, when `party.length > 1`, MULTIPLAYER_PROMPT) → frozen messages → mapped chat history → context message (combat state, enemies, party summary, active effects).
- **Tool calls are batched**: all tool calls from one LLM response run in **parallel** via `Promise.all`, then sorted by `id.localeCompare` for deterministic ordering. **Exception — turn-advancers are serialized**: `next_turn` is partitioned out and runs **after** all sibling action tools complete (the action tools still run in parallel among themselves). This prevents the parallel-batch race where a condition-applying tool (e.g. `cast_spell` Sleep applying `unconscious`) and `next_turn` race, letting an asleep enemy act because `next_turn`'s skip check evaluated before the condition landed. A defense-in-depth guard in `resolveEnemyTurn` (`combatService.ts`) re-checks `isIncapacitated(enemy) || isUnconscious(enemy)` before each enemy acts, so the bug is closed even if a future code path bypasses the ordering.
- **Prompt caching via sticky routing**: every LLM request body includes `session_id` (derived from `campaignId` via `buildSessionId()` in `services/llmClient.ts`). OpenRouter pins the session to a single provider endpoint, keeping the KV prompt cache warm across turns. The static prefix (system instruction + frozen checkpoints + tool schemas) is cached server-side after the first request — subsequent turns in the same campaign skip re-tokenizing those tokens. Cache hit rate is logged in debug mode (`[AgentLoop] Cache: iter=N cached=X/Y tokens`). For anonymous campaigns, the session ID is persisted in `localStorage` (`dor_anon_session_id`). The `session_id` is only injected for OpenRouter providers; non-OpenRouter bases ignore it.
- **End-of-turn detection**: `narrate_turn`, `long_rest`/`short_rest` (when called with `narration` **or** `autoAdvanceTime: true`), OR **any action tool carrying `narration`/`timePassed` or `narrationOnSuccess`/`narrationOnFailure` (gated out of combat)**. When detected: pre-narration tools execute first, then `narrate_turn` (skipped if time already advanced), then loop breaks.
- **Inline turn finalization**: deterministic tools (`update_inventory`, `adjust_currency`, `log_lore`, `upsert_quest`, simple `move_to`) can carry `narration`+`timePassed`+`suggestions`+`xp` to end the turn in one call. Binary dice tools (`check_skill`, `make_save`) can carry `narrationOnSuccess`+`narrationOnFailure`+`timePassed`+`suggestions` — the engine selects the correct branch from the actual roll outcome (zero-hallucination). The engine helper `maybeFinalizeTurn` (`mcpService.ts`) calls `narrate_turn` internally (forwarding `xp`) and merges the result. Only honored out of combat (OOC guard). Attacks and damage spells stay 2-call (numbers in prose require post-roll truthfulness). The prompt softens the single-call directive — the LLM is told it MAY end efficiently but secondary calls (`log_lore`, `upsert_quest`) are **encouraged** alongside the main action. If a separate `narrate_turn(xp=N)` arrives alongside an already-inline-finalized tool, the agent loop's `timeAlreadyAdvanced` branch still executes a `narrate_turn(timePassed=0, xp=N)` to capture the roleplay XP.
- **Multi-action synthesis path** (`agentLoop.ts`): when 2+ non-`narrate_turn` tools in one LLM response each carry inline-finalize args (out of combat), the agent loop defers finalize on all of them (they execute mechanically only — rolls, damage, location changes, but NO per-tool narration, gameTime advance, condition tick, or roleplay XP). This prevents two bugs that occurred when each tool independently called `maybeFinalizeTurn` → `narrate_turn` internally: (1) **gameTime stacking** — N parallel finalized tools each added their `timePassed` to `gameTime`; (2) **narration loss** — the agent loop's single-string `inlineNarration` capture (`break` on first ≥25-char result) silently dropped all but one tool's branch narration. The fix works in two modes depending on whether the LLM included an explicit `narrate_turn`:
  - **Multi-finalize + explicit `narrate_turn`**: the action tools are deferred (via `executeToolBatch`'s `options.deferFinalize`); the explicit `narrate_turn` IS the synthesis — it sees all resolved tool results in context and writes one coherent narration + `timePassed` + suggestions + xp. No extra LLM call. The existing `isEndOfTurn` block handles it.
  - **Multi-finalize without `narrate_turn`**: the action tools are deferred via the normal-path `executeToolBatch` (with `deferFinalize: true`), then a `SYNTHESIS_NUDGE` user message is appended telling the LLM to call `narrate_turn` to synthesize all results. The loop continues for one more iteration. A `synthesisExpected` flag guards the next iteration: if the LLM emits non-`narrate_turn` tools or empty content, it is re-nudged (max budget applies). When the LLM emits `narrate_turn`, the existing `isEndOfTurn` block processes it normally.
  - **Single-action turns are byte-identical**: `multiFinalize` is false (fewer than 2 finalizing tools), no deferral, inline finalize works exactly as before. The trigger is a pure count check on non-`narrate_turn` tools carrying finalize args.
  - **`deferFinalize` flag** (`mcpService.ts`): `maybeFinalizeTurn(args, baseResult, deferFinalize?)` early-returns `baseResult` when truthy (same as the combat guard). `executeToolCall(name, args, options?: { deferFinalize?: boolean })` threads the flag to each of the 8 finalize dispatch sites. The `validateTravelTimeAdvance` check is also skipped when deferring (the individual tool's `timePassed` won't be applied — the synthesis `narrate_turn` owns time advancement, and `narrate_turn` is intentionally not time-capped with `MAX_SAFE_EXHAUSTION` as the safety net).
- **`next_turn` causes immediate loop break** — the LLM cannot follow `next_turn` with `narrate_turn` in a later iteration. `narrate_turn` must be called before or simultaneously with `next_turn`.
- **Synthetic `narrate_turn(timePassed=0)` appended at loop end** if no time-advancing tool was called. This ensures conditions/DoTs/concentration always tick. The check is gated by `if (!timeAdvancedThisTurn)` — it is conditional, not unconditional.
- **No-tool-call retries**: raw `<tool_call>`/`<function>` text in content (model tool-calling format failure) → up to **2 corrective retries** with a targeted nudge before falling through to standard retries. Iter 0 empty → "You MUST call at least one tool". Iters 1-4 in combat (non-player turn only) → "call `next_turn`". Otherwise break. **Invalid tool-name filter** (`agentLoop.ts` `VALID_TOOL_NAMES`): a *different* format failure — the model emits a structured tool call whose `function.name` is the literal wrapper-tag name (`"tool_call"`, `"function"`) instead of a real tool — is handled by dropping the call before dispatch (debug-warn; no chat-log `[System:tool_call] Unknown tool` pollution). Filtering `rawToolCalls` at the source keeps the assistant echo / batch dispatch / tool messages all consistent (no orphaned `tool_call_id`s, since the reconstructed assistant message is built from the filtered list).
- **Post-loop guarantee**: if no `narrate_turn` / rest / inline-finalize fired, a synthetic `narrate_turn(narration='', timePassed=0)` is enforced so DoTs/conditions tick.
- **Critical tool failure** (`cast_spell`, `inflict_damage`, `roll_dice`, `player_attack`) sets `criticalToolFailed`, suppressing inline narration even if >= 50 chars.
- **Token budget checked AFTER batch execution**, not before — can't prevent an iteration from exceeding budget.
- **Tool results sent to LLM**: the function `formatToolResult` (`narration.ts:58-83`) produces a slim per-tool JSON for LLM context (no full `data` blob). This is the single path; `extractRollData` (`narration.ts:19-50`) provides rich data for the UI separately.
- **Per-character suggestions capture** (`agentLoop.ts`): when the LLM passes `suggestionsByCharacter` on `narrate_turn` args (multiplayer only), the agent loop normalizes and stores it as `result.suggestionsByChar`, which seeds Tier 0 of `resolveSuggestionsPerCharacter`. Solo never sets this; flat `result.suggestions` is used instead.

### Context pipeline (`services/llm/contextManager.ts`)
- **Active window**: last 20 messages, sent verbatim.
- **Frozen raw history**: older messages concatenated with `[Player]/[GM]/[System]` prefixes, capped at `VITE_CONTEXT_RAW_CAP` (30K tokens / 80K chars). Oldest 25% truncated when >80K chars.
- **Episode checkpoints**: LLM-generated summaries (~1.5K tokens, ~1000 words) written by summarization model. Append-only until eviction.
- **Compression triggers**: when `frozenRawTokens >= RAW_CAP` OR no checkpoints exist yet and `frozenRawTokens >= 1000`. Async, non-blocking.
- **Eviction (3-tier)**: 1) drop oldest checkpoints, 2) drop raw history, 3) trim oldest active messages (keep min 2).
- **Generation bumping on rewind**: `ctx.generation` incremented, stale in-flight compression results discarded by generation check.
- **Checkpoint compression prompt** (`atmosphere.ts:174-192`): dense ~1000-word archivist prompt preserving NPCs, quests, items, combat, skill checks, XP, lore, decisions. Uses `fetchWithTimeout` with a **120s primary timeout** and **one 180s retry on AbortError** (summaries are long-running; the old default 30s timeout caused silent `AbortError: signal is aborted without reason` failures). Also falls back to `message.reasoning_content` when `content` is empty.

## Key conventions

### State
- Campaign ID `'anonymous'` is the sentinel for local-only play (no Supabase sync). All persistence methods check this.
- Suggestions are stored per-character: `GameState.lastSuggestionsByCharacter: Record<string, string[]>` is the source of truth. Solo writes a single entry; multiplayer writes one per party member. The deprecated `lastSuggestions: string[]` field is read-only for old saves — never written by current code. Use `pickSuggestionsForCharacter(state, myCharacterId)` to read the correct slice.
- The ONLY way game time advances: `narrate_turn`, `long_rest`, `short_rest`, `move_to`, **or any action tool with inline narration** (`update_inventory`, `adjust_currency`, `log_lore`, `upsert_quest`, `check_skill`, `make_save`). A synthetic no-op `narrate_turn(timePassed=0)` is appended at loop end if no time-advancing tool ran (gated by `if (!timeAdvancedThisTurn)` at `agentLoop.ts:385-390`) so DoTs/conditions always tick.
- Never call `inflict_damage` after `player_attack` or `cast_spell` — those tools handle damage atomically.
- Spells never use `roll_dice`; spell attack rolls and damage are inside `cast_spell`.
- **`ensureCharacterFields()` / `ensureAllCharacterFields()` live in ONE place**: `services/characterUtils.ts`. Both `stateService` and `travelService` import it from there (not duplicated). `StateService.ensureCharacterFields()` delegates to `ensureAllCharacterFields(state.party)`.
- **`inflict_damage` lives in `InventoryService`**, not `CombatService`. Both CombatService and SpellcastingService depend on it. All damage in the system flows through one function.
- **Combat XP is auto-awarded on enemy defeat**: `awardEnemyDefeatXp` (`services/mcp/progressionService.ts`) hooks into `inflict_damage` — every kill path (player_attack, cast_spell, DoTs, enemy attacks) awards CR-based XP via `xpEngine.computeXp('combat', ...)` flat to all party members (no split, no solo buff) idempotently via the `Enemy.xpAwarded` flag.
- **Transactions**: deep-clone via `JSON.parse(JSON.stringify(...))`. 3-tier: transaction (in-flight rollback), rewind point (full state+messages per turn), emergency snapshot (crash recovery).
- **Duplicate currency detection**: `adjust_currency` is suppressed within 500ms for same target+amount. Cleared on `restoreSnapshot` and `reset`.
- **Enemy name auto-deduplication (Roman numerals)**: `generateUniqueEnemyName(input, existingEnemies)` (`services/mcp/combatService.ts`) is called inside `buildEnemyFromTemplate` (covers `add_enemy` + `start_combat` array) and inside `summon_creature` (`mcpService.ts`). When two+ enemies share the same base name, the engine auto-appends a Roman-numeral suffix: first enemy keeps the bare name ("Goblin"), subsequent duplicates become "Goblin II", "Goblin III", etc. Falls back to Arabic beyond X ("Goblin 11"). Does NOT fill gaps — picks next-after-highest. The LLM sees the unique names via tool results, combat context, battle map tokens, and initiative — zero prompt changes needed. Pure engine-side fix.
- **VTT battle map improvements**:
  - **Speed-limited drag-and-drop** (`BattleMapPanel.tsx` + layouts): Players can only drag their own character token (checked via `myCharacterId` prop). All drags are validated against the creature's speed — the move is blocked (token snaps back) if the Chebyshev distance exceeds `speed / 5` cells. Invalid drop targets render with a red fill + border. Speeds are computed via `calculateSpeed` for players and `beastFields.speed ?? 30` for enemies.
  - **Turn-based movement restriction** (`BattleMapPanel.tsx`): During combat, players can only drag their token on their own turn (`currentTurnId === myCharacterId`). Outside combat, free movement is allowed. The canvas cursor changes to `default` when it's not the player's turn.
  - **PLAYER MOVEMENT context** (`agentLoop.ts` + `GameState.lastTokenMove`): When a token is moved (via drag-and-drop or the `move_token` tool), `GameState.lastTokenMove` records `{ tokenId, from, to }`. The agent loop injects a `PLAYER MOVEMENT: <name> moved from (x1,y1) to (x2,y2) (N cells, N ft)` line into the LLM context, so the AI is aware of player-driven movement without requiring an LLM call. Cleared when combat ends or the map is dismissed.
  - **`setLastTokenMove`** (`mcpService.ts`): New public method that records the movement. Called by both `move_token` dispatch and layout `handleTokenMove` callbacks.
  - **Movement validation warning** (`mcpService.ts:468-492`): `move_token` calculates the Chebyshev distance from the token's current position to the target. It looks up the creature's speed (`calculateSpeed` for players, default 30 for enemies) and computes `maxCells = speed / 5`. If the move exceeds this, a `WARNING:` is appended to `result.message` (same warn-stamp pattern as the actor-id warning). The LLM sees it via `formatToolResult` and self-corrects. Does NOT block the move.
  - **Speed info in grid context** (`gridService.ts:buildGridContextString`): When called with an optional `speeds?: Record<string, number>` map, emits a `SPEEDS:` section listing each alive token's name, speed in ft, and max cells per turn. `agentLoop.ts` builds this map using `calculateSpeed` for players and 30 ft default for enemies.
  - **Grid coordinate labels** (`BattleMapPanel.tsx`): Canvas draws column numbers (0, 1, 2…) along the top edge and row numbers (0, 1, 2…) along the left edge in dim amber, matching the LLM context's (x, y) coordinate system.
  - **Melee-range hover ring** (`BattleMapPanel.tsx`): When hovering over a token, a dashed green ring is drawn at 1-cell radius (5 ft) around it, and the tooltip distance lines are tagged with `🗡 melee` for targets within 5 ft.
  - **Size-aware auto-placement** (`gridService.ts:findFreeCell`): `findFreeCell` now treats all cells occupied by a Large+ token's N×N footprint as occupied, preventing auto-placement from stacking on multi-cell creatures.

### Engine mechanics
- **Exhaustion** (levels 1-10; death at 10): applied as flat `d20Modifier: -level` on ALL d20 rolls (attacks, saves, checks, death saves) and `speedPenaltyFt: -(level * 5)`. Does NOT affect damage dice. **Travel-fatigue is hard-capped** at `MAX_SAFE_EXHAUSTION` (2): the `narrate_turn` exhaustion loop only applies levels 1..N, so the party can never die from a single journey — they must `long_rest` to climb higher.
- **Travel safety / no fast-travel** (`travelService.ts` + `mcpService.executeToolCall`): the named-route system is REMOVED — all travel is simple `move_to`. Two guardrails prevent accidental exhaustion death: (1) **leg cap** — `move_to`'s inline `timePassed` is rejected pre-dispatch if > `MAX_MOVE_TO_LEG_MINUTES` (240m / 4h), forcing long journeys into multiple legs with `long_rest` stops; (2) **fatigue ceiling** — the `narrate_turn` application loop caps travel exhaustion at `MAX_SAFE_EXHAUSTION` (2), so no single advance (via any tool) can be lethal. `narrate_turn` itself is NOT time-capped (legitimate narration time-skips like "a full day passes" still work); only the exhaustion *application* is bounded. Rests bypass both (`long_rest` clears exhaustion before advancing; `short_rest` is 60m).
- **Single canonical death save path**: `combatEngine.rollDeathSave()` is now a thin wrapper that delegates to `diceEngine.rollDeathSave()` (the two are unified, no longer independent). Exhaustion is applied via `getExhaustionPenalty()` inside `diceEngine`. The return now carries `rollSuccess: boolean` (true on nat-20/revive or `total >= 10`), threaded through the `roll_death_save` dispatch `data` and consumed by `extractRollData` so the `DiceRollCard` reflects whether **this** roll succeeded — NOT the pre-fix `isStable || successes >= 3` check, which made every successful save render as a failure until the 3rd success. **Durable feat is wired**: `diceEngine.rollDeathSave` calls `getDeathSaveBonus(char)` and adds the result to the roll total (nat 1 still crit-fails, nat 20 still revives — the bonus only affects the success/failure threshold for intermediate rolls).
- **Enemy attacks bypass `inflictDamageOnTarget`** — `resolveEnemySingleAttack` deals damage directly, skipping resistances/immunities/vulnerabilities/HAM/tempHP on targets. Enemy attack advantage/disadvantage flows through the same `resolveAdvantage` path as player attacks — it checks `attacksAgainstHaveDisadvantage` (e.g. Monk Patient Defense `dodging` condition) and `recklessAttacking` (Barbarian Reckless Attack grants advantage to incoming attacks) on the target, so conditions that impose disadvantage on incoming attacks are mechanically enforced for enemy attacks too.
- **Spell damage for save-based spells rolled independently per target** — each Fireball target gets its own damage roll. **Upcast scaling dice and cantrip-scaling dice are ALSO rolled fresh per target** and pushed into `result.damage.perTarget[]`; `result.damage.total` is recomputed as the sum of `perTarget` (so it is never larger than the sum). This fixes a prior bug where upcast/cantrip-scaling only bumped `total` and was silently dropped for save spells.
- **Save-spell damage reporting is a per-target breakdown** — the engine no longer emits a single pre-save `Σ-perTarget` as the damage "dealt" in `narrationHint` (which was both wrong — saves halve/negate it — and looked impossible next to one target's base dice). `spellcastingEngine` records only the save DC for save spells; `spellcastingService` builds a `damageBreakdown[]` ledger *as damage is applied* (post-save, per target) and renders `dmgSummary` as `DC X STAT save. <Name> <dealt> <type>[(saved)], ... (<totalDealt> <type> total)`. The reported total always equals the real HP lost (unless clamped at 0/death).
- **Save-spell saves are always rolled** when `spellDef.save` exists (the `make_save` dep is invoked per target; an LLM `targetSaveResults` override short-circuits the roll). `onSuccess:'half'` → half damage on success; `onSuccess:'none'` → 0 damage (e.g. Disintegrate). Condition spells (Hold Person, Bane, Web, …) likewise roll the on-cast save and skip `applyCondition` on a success — no spell in the catalog has both `damage` and `condition`, so the damage branch and condition branch never double-roll.
- **Temp-HP spells do not heal real HP** — when a healing spell's description mentions "temporary hit points" (False Life, Armor of Agathys), only `tempHp` is set; `hp.current` is left untouched.
- **Magic Missile upcasts** — darts = `dartCount + max(0, slotLevel - spell.level)` (3 base + 1/level above 1st).
- **Minute-duration conditions are skipped by round-based `tickConditions()`** — only `tickConditionsByTime()` handles them.
- **Conditions from concentration spells are tied by `source: spellId`** — when `breakConcentration` fires, ALL conditions with matching source are removed. Without `source`, conditions become orphans.
- **`isIncapsulated` typo** (conditionEngine.ts:217) must not be removed — it's an alias for `isIncapacitated` (at `:212`) and may exist in serialized game states.
- **Warlock pact magic** is the only short-rest slot reset. `recalculateResourcePools` (`classEngine.ts`) emits a single resource `{ id:'pactMagic', resetOn:'short', ... }` for warlocks from `classDef.spellcasting.pactMagic.slots[levelIdx]` (1–4 slots by level). `findSpellSlot`/`getMaxPactSlotLevel` key on `'pactMagic'`, so creating that resource is what makes the warlock castable. Warlock uses `pactMagic` (not `spellSlots`) — any code reading `spellSlots` blindly will break for warlocks. **Mystic Arcanum (6th–9th, once-per-long-rest) is NOT yet implemented** — only the pact-slot pool exists.
- **Fey Ancestry (elf/half-elf)**: grants `conditionsImmunities: ['sleep']` (so magical sleep is blocked — the Sleep spell's `hpPoolCondition` is the generic `'unconscious'`, so the service skips Fey Ancestry targets explicitly in the hpPool handler rather than via a broad `'unconscious'` immunity, which would wrongly block 0-HP knocks). Charm-save advantage is wired via the 4th `spellContext?: { isMagical?: boolean; isCharm?: boolean }` arg on `combatService.make_save` / `SpellcastingDeps.make_save`. `cast_spell` passes `{ isMagical: true, isCharm: spellDef.condition?.type === 'charmed' }` for EVERY spell-originated save: `isMagical` unlocks Gnome Cunning (INT/WIS/CHA saves vs magic) on all spell saves, and `isCharm` unlocks Fey Ancestry (charm saves roll twice, keep higher) only for charm-condition spells. The LLM-driven ad-hoc `make_save` tool passes no spell context (documented limitation). `make_save` rolls the d20 BEFORE `applyEffects('onSaveRoll')` so the `reroll-ones` reducer (Halfling Lucky) can replace a natural-1 save.
- **`sanitizeNarration`** (`utils/textSanitize.ts`): strips `<tool_call>`/`<function>` blocks, ChatML special tokens (`<|im_end|>`, fullwidth variants), and `[System:…]` prefixes from any narration text. Applied at three layers: engine-side (narrate_turn dispatch, maybeFinalizeTurn, cast_ritual), inside generateNarration/generateNarrationStream returns (defense-in-depth), and at the ultimate chokepoint (`finalNarration` → `modelMsg.text` in useGameActions) so no LLM-sourced text reaches the bubble unsanitized.
- **`maybeFinalizeTurn`** (`mcpService.ts`): engine helper that collapses action+narrate_turn into one call. For deterministic tools, reads `narration`/`timePassed`/`xp` from args and calls `narrate_turn` internally (forwarding `xp`). For binary dice tools (check_skill, make_save), reads `narrationOnSuccess`/`narrationOnFailure` and selects by the actual roll result. OOC guard: only honored when combat is not active. In ALL finalize paths (this helper **and** `long_rest`/`short_rest` in `travelService.ts`), narration prose goes ONLY into `data.narration` (→ bubble); it is never appended to `message` (→ `[System:<tool>]` log), which would duplicate the bubble. `message` keeps mechanical details + time-advancement logs only. Roleplay `xp` and the `roleplay` tag (`'dialogue'\|'creative'`) are forwarded from inline-finalized tools to the internal `narrate_turn` call.
- **`awardEnemyDefeatXp`** (`services/mcp/progressionService.ts`): called automatically by `inflict_damage` when an enemy drops to 0 HP. Awards CR-based XP flat to all party members via `xpEngine.computeXp('combat', ...)`, guarded by `Enemy.xpAwarded` flag for idempotence.

### XP system (`services/xpEngine.ts`)
- **Centralized engine**: ALL XP awards flow through `computeXp(trigger, ctx)` (pure amount) → `awardXpToParty(state, amount)` (flat to every party member). No party splitting, no solo buff. One config table to tune game feel.
- **6 triggers**: `combat` (CR-based), `skill` (DC-bracketed, nat 20 = ×2), `explore` (first visit, `significance`-tiered), `quest` (`difficulty`-tiered on completion), `lore` (flat 10 per new entry), `roleplay` (auto-awards 1 XP baseline on every non-combat `narrate_turn` with non-empty narration; `roleplay: 'creative'` tag or explicit `xp` param boosts up to 10; clamped 1-10; explicit `xp=0` suppresses).
- **No `award_experience` tool**: removed entirely. The LLM never calls an XP tool — XP flows through tool parameters (`significance` on `move_to`, `difficulty` on `upsert_quest`, `xp` on `narrate_turn`) and engine-side auto-awards (combat kills, skill checks, lore entries).
- **Exploration XP**: `move_to` checks `state.visitedLocations` (string array, party-wide). First visit awards XP; re-visits do not. Omitted `significance` defaults to landmark (100 XP).
- **Quest XP**: `upsert_quest` awards on `status → 'completed'` transition, guarded by `Quest.xpAwarded` flag for idempotence. `Quest.difficulty` (trivial/easy/medium/hard/deadly) controls the bracket.
- **Lore XP**: `log_lore` is title-deduped (case-insensitive). Duplicate titles are rejected (prevents XP farming). Each new entry awards flat 10 XP.
- **Types**: `QuestDifficulty` and `LocationSignificance` in `types/game.ts`. `GameState.visitedLocations?: string[]`, `Quest.difficulty?`, `Quest.xpAwarded?`.

### Character creation
- **Prepared vs Known caster asymmetry**: `buildCharacterFromWizard` sets `knownSpells` = cantrips only for prepared casters (wizard/cleric/druid/paladin), and `preparedSpells` = cantrips + selected spells. Known casters (bard/sorcerer/warlock/ranger) get both in `knownSpells`. The wizard UI only enforces max spells for known casters. **Non-casters emit empty spell arrays** — the build service gates on `selectedClass.spellcasting` (defense-in-depth; `ClassStep` also clears `selectedSpells`/`selectedCantrips` on class switch so a caster→non-caster switch leaves no phantom spells). **Post-creation management** differs by caster type (see "Spellbook Management UI" below): prepared casters re-prepare freely out of combat via the SpellbookModal; known casters only swap on level-up (Tasha's rule) via the same modal.
- **Half-Elf ASI is the string `'flexible-2'`**, not a normal `Record<string, number>`. Triggers +2 CHA + two +1 choices. Resolved everywhere via `getEffectiveAsiMap(race, subraceId, he1, he2)` (`components/creation/asiUtils.ts`) — the single source for the effective per-stat racial bonus map, used by FeatsStep (stat caps), GearStep (AC preview), StatsStep (HP preview + bonus allocator), and ReviewStep (summary).
- **ASI/Feat slot indexing**: `asiFeatSlots` array index maps to `ASI_LEVELS[idx]` (`[1, 4, 8, 12, 16, 19]`). The `FeatSelection.level` field is NOT stored in wizard state — set during finalization.
- **`skilled` feat inlines skill allocations** — bypasses normal skill point pool, added in post-processing.
- **`goldPool` is floating point**: integer part = GP, fractional = SP (`12.5` = 12 GP, 5 SP). Uses `toFixed(2)` to avoid drift. The build service rolls SP ≥ 10 into GP at finalize (e.g. `12.98` → 13 GP, 0 SP).
- **Skill points are a house rule**: `computeSkillBudget(classDef, level)` (`components/creation/skillPoints.ts`) = `skillChoices.count * 2` at L1 + 3/level (4 for Rogue) thereafter. Single source of truth shared by WizardShell, SkillsStep, and `buildPresetCharacter`. Previously triplicated.
- **`STAT_POINTS_PER_LEVEL = 2` is a parallel stat-progression house rule** separate from ASI slots. High-level characters get `(level-1)*2` bonus stat points; the Stats step exposes a "Bonus Ability Points" allocator (when `level > 1`) that spends down this budget into `WizardState.bonusStatAllocations`. The build service applies them to `fs` and sets `unusedStatPoints` to the unspent remainder. Unspent points carry into play for later allocation.
- **Stats step transient state is persisted in `WizardState`** (`statsGenMode`, `rolledStatValues`, `rollHistory`) so navigating away and back no longer wipes the chosen generation mode, rolled dice, or allocated stats. Mode-switch reseeding lives in the tab `onClick` (a real user action), NOT a mount `useEffect`.
- **`level_up` tool dispatches to `allocateStatPoints`**, not the full level-up flow. The actual level-up validation happens elsewhere.
- **Gear step equips gear**: bought weapons/armor/shields auto-equip when the slot is empty (mirroring starting equipment), and each inventory row has an equip toggle that enforces one-armor + one-shield max. Sells are per-unit (decrement quantity, refund half the SRD-derived base price). Sell base = shop price if in `SHOP_ITEMS`, else parsed SRD `cost`, else 2 GP.
- **Spell selection level cap is slot-derived**: SpellsStep computes the highest castable level from `selectedClass.spellcasting.spellSlots[level-1]` (last non-zero index), with warlock pact-magic fallback. No longer shows/selectable spells above the character's actual slot level.
- **Class/level reset split**: changing `selectedClass` resets inventory/gold/allocatedSkills (different starting kit); changing `level` does NOT (preserves gear purchases and skill picks). Only the ASI-slot count adjusts on level change.
- **`handleCharacterCreated` always aligns location with the campaign's starting ground**: it sets `character.location = startingLoc.name` whenever the engine has a `startingLocation` (the guard is `if (startingLoc)`, NOT `if (!character.location && startingLoc)`). Both the QuickStart preset path and the custom-wizard build can leave a fallback location (e.g. "The Rusty Tankard Tavern") baked into the built character; overriding here guarantees a freshly-created host or joiner spawns at the actual chosen/generated starting ground. The chat intro narration also dropped its hardcoded "hooded figure" fallback — it now uses the generated `startingLoc.introHook`, falling back to the generated `startingLoc.description` (both LLM-authored and thematic) rather than injecting a generic tavern hook. The `STARTING_LOCATIONS_PROMPT` was strengthened to mandate a non-empty `introHook` per location, and the `generateStartingLocations` parser falls back to the description when the LLM omits the field, so the preview card always renders something.
- **Starting location generation timeout & retry**: `generateStartingLocations` calls `fetchWithTimeout` with a **180s timeout** (up from the default 30s). `fetchWithTimeout` (`llmApiClient.ts`) accepts an optional 4th `externalSignal` param — if provided, a user-initiated abort (via the retry button) cancels the in-flight request by forwarding to the internal timeout `AbortController`. In `QuickStartFlow`, a **Retry button** appears after **60s** of `isGenerating` via a `useEffect` timer (`showRetry` state). Clicking it: aborts the current `AbortController`, resets `showRetry`, and restarts `fetchLocations`. Stale call cleanup is handled by the existing `generationIdRef` guard. The `genFailed` retry button and the "Reroll" button also abort any lingering request before starting a new one.
- **`WizardStep.validate` was removed** as dead code — it was never invoked by `StepWizard`. Real validation lives in each step's continue handler and `WizardShell.handleFinalize`.
- **`buildCharacterFromWizard`** (8-step): name validation → location resolution → base stats → racial ASI + bonus allocations → ASI/feat slots → con mod & racial traits → resource pools → assemble final Character. HP is computed through `calculateMaxHp` after assembly so HP-affecting effects (Hill Dwarf Dwarven Toughness +1/level, Draconic Bloodline +level via `sorcerousOrigin`, Tough feat) apply at creation — for characters with none it equals the old inline formula. **New characters only** — existing saved characters keep their HP to avoid clobbering GM hand-adjustments.
- **Background & Persona step** (`components/creation/BackgroundStep.tsx`, inserted between `gear` and `review`): the dedicated SRD 5.1 persona step. Entirely optional (NavBtn never disabled). The free-text `backstory` textarea was MOVED here from `NameStep` (NameStep now captures only name + level). See "Background & Persona (SRD 5.1)" below for the full system.

### Subrace System
- **Subrace definitions** (`data/races.ts` `SubraceDefinition`): Elf (High Elf, Wood Elf, Drow), Dwarf (Hill Dwarf, Mountain Dwarf), Halfling (Lightfoot, Stout), Gnome (Rock Gnome, Forest Gnome), and Human (Standard, Variant) all have `subraces?: SubraceDefinition[]`. Each subrace can add ASI bonuses (`asi`), override darkvision, add speed bonus (`speedBonus`), and grant additional traits (`traits` with full effect-payload support).
- **`RaceStep` subrace picker** (`components/creation/RaceStep.tsx`): shows a subrace selection card grid when the selected race has subraces. Not required — the player can proceed without selecting (defaults to base race). Cleared on race change (`updateWizard({ selectedSubraceId: null })`).
- **`WizardState.selectedSubraceId`** (`components/creation/types.ts`): stored on the character as `subraceId` during `buildCharacterFromWizard`. **REPLACE ASI semantics**: when a subrace is selected, its `asi` IS the full racial ASI package — the base race ASI is ignored (base ASIs already include the subrace-specific +1, so summing both double-counts; e.g. Elf base `{dex:2,int:1}` + High Elf's subrace `{dex:2,int:1}` = exactly the SRD High Elf, not `+2 INT`). `getEffectiveAsiMap` (`components/creation/asiUtils.ts`) takes `subraceId` so creation-step previews (stat caps, AC, HP) match the built stats. Subrace traits are added to `racialTraits[]` AND registered in the effect dispatcher via `getEffects()` subrace lookup (checks `race.subraces.find(sr => sr.id === character.subraceId)`).
- **Notable subrace effects**: Hill Dwarf's Dwarven Toughness (`hp-per-level: { amount: 1 }`), Stout's poison resistance + save advantage, all via standard effect payloads — zero engine code changes.

### Fighting Style System
- **Fighting Style choice** (`data/classes.ts`): Fighter L1, Paladin L2, Ranger L2 features carry `effect: { kind: 'fighting-style' }` + `choice: { options: FIGHTING_STYLE_OPTIONS }`. The `FIGHTING_STYLE_OPTIONS` array includes Archery, Defense, Dueling, Great Weapon Fighting, and Two-Weapon Fighting. **Protection is NOT offered** — it requires battle-map adjacency the engine can't enforce, so all class pickers filter it out (no trap option).
- **`ClassStep` fighting style picker** (`components/creation/ClassStep.tsx`): shows a style selection grid when the class has a fighting-style feature at or below the character's level. Selection stored in `WizardState.fightingStyleChoice` → `Character.fightingStyle`. Cleared on class change.
- **Level-up auto-assign** (`hooks/useProgression.ts:handleConfirmAllocation`): when a class-level fighting-style feature is unlocked during level-up, auto-assigns `'defense'` as a default if the character doesn't already have a style. Lives in `handleConfirmAllocation` (NOT `handleAcknowledgeSubclass`) because class features (Fighter L1, Paladin L2, Ranger L2) aren't subclass features — the code itself comments this. Champion's L10 `additional-fighting-style` (a subclass feature) writes to `Character.fightingStyleTwo` via the level-up flow. The player can change either style later via the LevelUpModal.
- **Engine application** (`services/effectDispatcher.ts` + `services/mcp/combatService.ts`): the `fighting-style` reducer applies Defense (+1 AC in armor), Archery (+2 attack — written to `ctx.attackBonus`, kept off the natural d20 so `isCrit` uses the true roll), Dueling (+2 melee damage). GWF rerolls 1s/2s on damage dice, and TWF adds ability mod to offhand damage — both checked via `character.fightingStyle` in `combatService` alongside the existing `gwf-reroll`/`offhand-modifier` feat effects.

### Eldritch Invocations
- **`data/invocations.ts`**: `INVOCATIONS_CATALOG` with 8 invocations (Agonizing Blast, Armor of Shadows, Fiendish Vigor, Repelling Blast, Devil's Sight, Eldritch Sight, Mask of Many Faces, Thirsting Blade). Each carries an `effect` tag (`'agonizing-blast'`, `'at-will-spell'`, `'extra-attack'`, `'passive'`) and optional `grantsSpells[]`. `getInvocationCount(level)` returns the warlock's invocation budget (2 at L2, up to 8 at L18).
- **`ClassStep` invocation picker** (`components/creation/ClassStep.tsx`): shown for Warlocks at L2+. Multi-select with count limit enforcement. Selection stored in `WizardState.invocationChoices` → `Character.invocations`.
- **Level-up invocation picker** (`components/LevelUpModal.tsx` "Invocations" tab): shown when `Character.pendingInvocations > 0`. `awardExperience` (`services/progressionService.ts`) grants `pendingInvocations` when leveling past the L2/L5/L7/L9/L12/L15/L18 thresholds — the delta between `getInvocationCount(newLevel)` and the invocations already chosen. Threading: `ProgressionContext` → layouts → `LevelUpModal onConfirmInvocations` prop.
- **Engine effects**: Agonizing Blast (`spellcastingEngine.ts` — adds CHA mod to each Eldritch Blast beam damage, annotation appended to the correct beam's detail string). At-will spells (Armor of Shadows → mage armor, Fiendish Vigor → false life, etc.) are added to `knownSpells` during character creation AND via `choose_invocations` at level-up. At-will spells are exempt from slot consumption in `castSpell` and excluded from the known-spell cap in `canLearnSpell`; they are also guarded against forget/swap in `spellcastingService`. Thirsting Blade (a pact-weapon Extra Attack) is enforced via the `TOOL_MODE_INSTRUCTION` prompt (the LLM issues two `player_attack` calls — same as martial Extra Attack; no engine reducer).
- **`Character.invocations?: string[]`** (`types/character.ts`): initialized to `[]` by `ensureCharacterFields`. **`Character.pendingInvocations?: number`**: initialized to `0`. **`choose_invocations`** rejects duplicate selections within the input array (not just against existing invocations).

### Barbarian: Reckless Attack
- **`player_attack` `reckless` parameter** (`tools/combat.ts` + `combatService.ts`): when set true and the attacker has the `reckless-attack` effect, the engine grants advantage on the melee STR attack and sets `Character.recklessAttacking = true`. While `recklessAttacking` is true, `resolveAdvantage` grants advantage to attackers targeting the barbarian (mechanically enforced — not narrative-only).
- **Flag lifecycle**: `recklessAttacking` is cleared at the start of the barbarian's next turn (the `next_turn` cleanup block at `combatService.ts:700`) and on new-round rollover (the new-round path at `combatService.ts:665` clears the flag for ALL party members, since Reckless Attack only applies during the barbarian's own turn).
- **Tool schema**: `reckless: boolean` parameter on `player_attack`. The prompt instructs the LLM to pass it only for Barbarian L2+ melee STR attacks.

### Monk: Ki & Unarmed Strikes (mechanically enforced via resource handler)
- **Monks are NOT spellcasters** — the monk ki pool exists in `recalculateResourcePools` at `classEngine.ts:263` (pool = monk level, reset on short rest). Stunning Strike works via `use_resource('ki', targetId)` → the `ki` handler in `resourceHandlers.ts` auto-rolls the target's CON save and applies the stunned condition on failure (the handler reads `make_save.data.success` as "save passed", so a failed save correctly lands the stun). Monks have no spell list. The `TOOL_MODE_INSTRUCTION` prompt forbids calling `cast_spell` for monk abilities. Unarmed strikes map to `player_attack` with `weaponName="Unarmed Strike"` (Martial Arts die: 1d4 + DEX, scaling 1d6 @ L5, 1d8 @ L11).
- **Ki sub-action selection** (`resourceHandlers.ts`): the `ki` handler dispatches on a normalized `targetId` (`toLowerCase().trim().replace(/[_\s]+/g, '-')`), so `'flurry-of-blows'`, `'Flurry of Blows'`, `'flurry_of_blows'`, etc. all work. Non-matching ids route to Stunning Strike (enemy name). Patient Defense applies a stable `{ id: 'dodging', duration: 1 }` condition, which `conditionEngine.getConditionEffects` now maps to `attacksAgainstHaveDisadvantage` — and `combatService.resolveAdvantage` consumes it, so incoming attacks on a dodging monk roll with disadvantage (mechanically enforced, not just narrated).
- **Ki features are level-gated by prompt**: ki points unlock at Monk L2 (pool = monk level). Flurry of Blows / Patient Defense / Step of the Wind each cost 1 ki and are forbidden for a level-1 monk — the prompt instructs the LLM to narrate "has not yet learned to channel ki" instead.

### Persistence
- **Sync coalescing**: `enqueueSync`/`drain` batches multiple `syncCampaignState` calls within the same microtask into a single Supabase `UPDATE`. Uses `queueMicrotask`, not `setTimeout`. Merge semantics: multiple calls for same campaignId within one tick are merged.
- **Supabase Proxy** (`supabaseClient.ts`): `then`/`catch`/`finally` return `undefined` to prevent the proxy from being treated as a thenable/Promise. All other properties delegate to the real client with methods auto-bound.
- **Supabase tables**: `campaigns(id, host_id, name, game_state JSONB, messages JSONB)`, legacy `game_saves`, `srd_items`, `srd_monsters`. The runtime uses static TS catalogs (`data/`) — SQL tables are for community tooling.
- **auditor.ts**: 16 audit rules (hp-bounds, currency-non-negative, inventory-quantity-non-negative, character-location-exists, unique-lore-entries, quest-id-unique, xp-non-negative, unused-stat-points-valid, experience-to-next-level-positive, feats-valid, classes-valid, races-valid, spells-valid, proficiency-valid, game-time-valid, last-long-rest-valid) with auto-repair. Not wired into runtime, available for diagnostics/tests. Each rule mutates a running copy of state.
- **`cryptoRoll`** (`utils/random.ts`): rejection sampling over `Uint32Array(1)` from `crypto.getRandomValues` to avoid modulo bias. Falls back to `Math.random()` if crypto unavailable.
- **Streaming client** (`services/streamingClient.ts`): async generator parsing SSE. 60s read-timeout watchdog reset on every `reader.read()`. Yields `content`, `reasoning`, `tool_calls`, `usage`, `done`, `error` chunks.

### Agent loop prompts
- **`SYSTEM_INSTRUCTION`** (`constants.ts:8-39`): 14 numbered rules (mandatory tool usage, currency math, equipped weapon narration, time/durations, English only, etc.)
- **`PROGRESSION_SYSTEM_PROMPT`** (`constants.ts`): engine-driven XP system documentation — explains the 6 auto-award triggers (combat, skill, explore, quest, lore, roleplay) and how the LLM triggers each via tool parameters (`significance` on `move_to`, `difficulty` on `upsert_quest`, `xp` on `narrate_turn`). No XP tables (engine owns them). Long-rest cooldown mechanics.
- **`TOOL_MODE_INSTRUCTION`** (`services/llm/prompts/toolModePrompt.ts`): strict combat sequence, quick reference table, 11 feat descriptions, class feature narration, race trait guidance, spell prerequisites, ban on `[System:tool_name]` in narration, plus ban on emitting `<tool_call>`/`<function>` markup in content or narration (only use the structured `tools` parameter). Includes a "MULTIPLE ACTIONS IN ONE TURN" section that MANDATES a `narrate_turn` IN THE SAME RESPONSE as multiple action tools — sending action tools without a `narrate_turn` forces an extra synthesis round-trip (10+ seconds).
- **Narration fallback chain** (4 tiers, in `useGameActions.ts` + `services/llm/narration.ts`): 1. `inlineNarration` from the agent loop (captures narration from tool results / `narrate_turn` args / `next_turn` deterministic prose — **NOT** from `reasoning_content` and **NOT** from assistant prose emitted alongside tool calls; see the no-bleed rule below); 2. `generateNarration` retry (must be ≥25 chars post-sanitize); 3. `generateNarrationSimple` — minimal-prompt LLM retry at `temperature: 0.9`, fires only when tiers 1+2 produced nothing usable; 4. `buildDeterministicNarration(toolMessages)` — zero-LLM one-liner derived from the turn's `rollData` (e.g. "The strike lands for 12 damage."), always truthful; → finally literal `"The adventure continues..."` (only when no tool data exists). All four tiers share the ≥25-char post-sanitize gate except tier 4 which produces short deterministic strings. `resolveNarration` (`useGameActions.ts:157-162`) is still a degenerate stub returning `inlineNarration ?? 'The adventure continues...'`; the tiered logic lives directly in `handleSendMessage`/`handleProcessBatch`. **`reasoning_content` handling (no-bleed rule)**: the narration paths (`generateNarration`, `generateNarrationSimple`, and the agent loop's `lastNarrationCandidate`/`inlineNarration` capture) use `message.content` ONLY — they NEVER fall back to `message.reasoning_content`. For a reasoning model (deepseek-v4-flash), `reasoning_content` is genuine chain-of-thought (planning, math, decisions — e.g. breaking a multi-leg journey into travel chunks), not in-world prose; treating it as narration caused the model's internal "thinking" to bleed into the chat bubble. An empty `content` result yields empty text and falls through the tier chain. The agent loop additionally gates its `lastNarrationCandidate` capture on `rawToolCalls.length === 0` (prose alongside tool calls is the model describing what it is about to do, not narration) and dropped the prose-alongside-tools fallback entirely. ONLY `compressRawToCheckpoint` (summarization, never shown in the bubble) still falls back to `reasoning_content` when `content` is empty. **Retry hard-cap**: tiers 2 and 3 are wrapped in `withNarrationRetryTimeout` (45s `Promise.race`) so a hung retry LLM call can never pin `isLoading` and freeze the chat on "The Fates are deciding...". **`generateNarration` abort coverage**: the 60s `AbortController` timer is cleared in a `finally` (NOT after the fetch headers arrive), so it covers `response.json()` too — a gateway that stalls on the body can't hang the call forever. **`inlineNarration` capture fallback** (`agentLoop.ts`): if `data.narration` comes back empty (or `timeAlreadyAdvanced` skipped re-executing `narrate_turn`), the narration the LLM supplied directly in the `narrate_turn` args is used, avoiding a slow retry whenever the model already provided prose. **`insertToolCallMessages` non-TOOL guard** (`useGameActions.ts`): when `narrate_turn` fires an ambient time-of-day transition or condition expiry, it pushes a `MessageRole.SYSTEM` message directly into `toolMessages`. Without a role guard, the outer `while` loop's inner batch collector would stall forever on that non-TOOL message (inner while fails immediately, `i` never increments → infinite loop → browser freeze → "The Fates are deciding..." stuck). The guard passes any non-TOOL message straight through to the output array so `i` always advances; ambient/condition log messages now also appear correctly in the chat.
- **Combat narration via `next_turn`**: combat is driven by `next_turn`, which produces no narration prose of its own and breaks the loop before the narration-capture block (`agentLoop.ts:416`). The engine attaches a deterministic `data.narration` (built from resolved `attackResults[]`, zero-hallucination) and `data.suggestions` (contextual: heal wounded / attack / cast) to the `next_turn` result in `combatService.next_turn`. The agent loop captures both at the break point (`agentLoop.ts:416-440`) so the fallback and empty suggestion tray never fire during combat. LLM-provided narration (via `narrate_turn`) still takes priority.
- **Suggestion system — per-character 4-tier chain** (`resolveSuggestionsPerCharacter` in `services/llm/suggestions.ts`, called from `handleSendMessage` + `handleProcessBatch` after narration). Replaces the legacy single-list model. Returns `Record<characterId, string[]>` stored as `GameState.lastSuggestionsByCharacter`. Solo produces a single-entry record; multiplayer produces one entry per alive party member. Each character's chips are **class-aware**: Rogue → Sneak Attack / Scout, Cleric → Channel Divinity / Cast Healing Spell, etc. **Tier 0** — inline per-character suggestions from agent loop (`result.suggestionsByChar`, from `narrate_turn.args.suggestionsByCharacter` in multiplayer; solo collapses flat `suggestions` to a one-entry map). **Tier 1** — one structured LLM call `generateSuggestionsPerCharacter` returning a per-character map (same cost as legacy single call, 20s `withSuggestionsTimeout`). **Tier 2** — deterministic per-character: `buildCombatSuggestions(state, charId)` (class-flavored attack verbs + self-heal vs potion) or `buildExplorationSuggestions(state, charId)` (class fantasy + per-character state). **Tier 3** — `GENERIC_SUGGESTIONS` per character. **Disappear-on-select**: the layout suggestion prop is gated on `!gameState.isProcessing` — chips hide the instant a turn locks (`isProcessing: true` at the lock step) and only reappear when `syncFinished` sets `isProcessing: false` alongside the fresh suggestion map (same `setGameState` call, no flicker). **The per-player clear (deleting the local entry from `lastSuggestionsByCharacter`) is now the authoritative disappearance mechanism for the "I typed/clicked → my chips vanish" UX** — it fires in both the multiplayer `handleSendMessage` pending branch (the moment a player adds a pending message) and the solo/batch pre-turn clear. Only the acting player's chips clear; everyone else keeps theirs until they act or the batch runs. **Error-path fallback**: catch blocks iterate every alive party member and write per-character recovery chips. **`pickSuggestionsForCharacter(state, charId)`** helper reads the per-character map. When the map exists, it IS authoritative — no fallthrough to the deprecated `lastSuggestions` field (which shares the same mutable object reference and gets repopulated by the agent loop during processing, causing chips to reappear if fallthrough were allowed). Falls back to `lastSuggestions` only when `lastSuggestionsByCharacter` is absent entirely (old saves).
- **`extractRollData`** (`narration.ts:20`): extracts structured `RollData` from tool results for UI display. Covers `roll_dice`, `check_skill` (label = skill name via `data.skillName`, falling back to `data.character`), `player_attack`, `cast_spell`, `make_save`, `roll_death_save`, `inflict_damage`, `use_resource`, and `next_turn`. Returns a `RollData[]` when multiple cards are needed — `player_attack` (attack + damage card on hit), `cast_spell` (attack + damage card when both exist), `next_turn` (attack + damage card per resolved enemy attack). Single rolls return a `RollData` object. Return type is `RollData | RollData[] | undefined`.
- **`Message.rollData`** (`types/common.ts:76`): `RollData | RollData[]` — supports multiple cards per message (e.g. multi-enemy `next_turn`). `ChatLog.tsx` normalizes to an array for rendering. Old persisted single-object messages remain valid.
- **Dice roll auto-trigger** (`ChatLog.tsx`): a `useEffect` watches for newly-arrived messages (by ID) that carry `rollData` and calls `onTriggerDiceRoll(buildReplayData(roll))` for each, with 4 s staggered delays to prevent modal overlap. A `mounted` ref skips initial-load messages so campaign hydration doesn't trigger animations. Runs on every client — local and remote via Supabase realtime — so all players see the dice roll modal popup, not just the one that submitted the turn. `DiceRollCard` remains clickable for manual replay.
- **`formatToolResult`** (`narration.ts:58-83`): produces a slim per-tool JSON for the LLM context (the `tool` messages fed to each subsequent iteration). This is the single source of truth for what the LLM sees; the full `data` blob is never sent back.

- In production, set `VITE_LLM_API_BASE=/api` to route through the Vercel proxy (`api/chat/completions.ts`), solving CORS.
- `VITE_LLM_PROXY_TARGET` overrides the proxy target. Three-tier fallback: `VITE_LLM_PROXY_TARGET` → `VITE_LLM_API_BASE` → `https://opencode.ai/zen/go/v1`.
- Env vars accessed via `getEnv()`: tries `import.meta.env` first, falls back to `process.env`. Never throws. **Truthy-only**: empty strings return `undefined`.
- `VITE_LLM_DISABLE_THINKING=true` disables reasoning traces (sends `{ thinking: { type: 'disabled' } }`).
- **preflight.js** requires `.env` to contain the literal string `VITE_SUPABASE_URL` to skip setup mode. Even `VITE_SUPABASE_URL=` (empty value) satisfies this.

## Build quirks
- `npm run dev` goes through `scripts/preflight.js` (auto-install, env check) before spawning `vite` as a child process. Not a direct `vite` call.
- Setup mode is detected TWICE: `preflight.js` sets env var, `vite.config.ts` re-verifies by reading `.env`. Config wins.
- Build chunking: 4 vendor chunks (`vendor-react`, `vendor-supabase`, `vendor-vercel`, `vendor-ui`). Everything else in default chunk.
- Vitest `include` is `tests/**/*.test.{ts,tsx}` (not alongside source). `css: true` processes CSS imports. `globals: true` makes `describe`/`it`/`expect` available without imports.
- **Untested services**: `services/llm/contextManager.ts`, `services/mcp/partyService.ts`, `services/supabaseClient.ts` have no direct test coverage. Be cautious editing them.

## Type system invariants
- `Character.stats` is always `{ str, dex, con, int, wis, cha }` — exactly 6 keys. Same for `Enemy.stats?`.
- `Character.hp.current` is clamped to `[0, max]` by every tool that modifies HP. Same for `hitDice.current` and `resources[].current`.
- `SpellDefinition.level: 0` = cantrip. Cantrips use `cantripScaling`, levelled spells use `scaling`.
- `ActiveCondition.durationUnit` defaults to `'round'` when undefined. `'minute'`/`'permanent'` skipped by `tickConditions()`.
- `CombatState.isActive` must be true when `combat` is present. `initiative` must have >= 1 entry, `round >= 1`.
- `Character.subclassId` and subclass-specific fields (`divineDomain`, `sorcerousOrigin`, `warlockPatron`, `arcaneTradition`, `fightingStyle`, `sneakAttackDice`, `draconicAncestry`) are mutually exclusive by class.
- `ReactionAvailable` / `ReactionUsedThisTurn` pair: `reactionUsedThisTurn = false` reset at start of each character's turn.
- `CombatState.activeDoTs[].remainingRounds: null` = indefinite (persists until saved against or dispelled).
